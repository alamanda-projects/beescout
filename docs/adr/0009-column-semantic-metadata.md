# ADR-0009: Blok `semantic` opsional per kolom — metadata bisnis machine-readable

**Status**: Proposed
**Tanggal**: 2026-07-25
**Decider**: @haninp

---

## Konteks

Kontrak BeeScout sudah kaya metadata kolom — `business_name`, `description`, `logical_type`, `physical_type`, quality rules, `tags`. Semuanya **human-readable**: berguna untuk dokumentasi dan tata kelola, tapi tidak bisa ditafsirkan mesin.

Konsekuensinya, BeeScout tidak punya cara mengetahui bahwa dua kolom di dua dataset berbeda merepresentasikan konsep bisnis yang sama:

```yaml
- column: uid
  business_name: User ID
  description: User identifier column.
# vs kontrak lain
- column: customer_no
  business_name: Customer Number
  description: Customer identifier generated by CRM.
```

Keduanya adalah *Customer Identifier*, tapi bagi BeeScout dua kolom yang sama sekali tak berhubungan. Ini menutup pintu ke schema mapping otomatis, integrasi glosarium, pencarian semantik, dan visualisasi lineage yang lebih baik — kapabilitas yang mulai dibutuhkan konsumen eksternal (HoneyGrade, [#145](https://github.com/alamanda-projects/beescout/issues/145)).

Diskusi maintainer 2026-07-25 (terekam di [#162](https://github.com/alamanda-projects/beescout/issues/162)) menimbang empat pendekatan:

1. **Blok `semantic` opsional per kolom** di dalam `model[]`
2. Semantic Registry terpisah + referensi dari kolom
3. Perluas `tags[]` dengan konvensi penamaan (`entity:Customer`, `concept:Identifier`)
4. Tidak menyimpan di kontrak — serahkan ke katalog metadata eksternal

## Keputusan

**Kandidat 1 — blok `semantic` opsional pada setiap entri `model[]`.**

```yaml
model:
  - column: uid
    business_name: User ID
    logical_type: string
    physical_type: varchar(36)
    description: User identifier column.

    semantic:
      entity: Customer          # entitas bisnis
      concept: Identifier       # makna di dalam entitas → "Customer.Identifier"
      canonical: true           # apakah ini representasi kanonik konsep tsb
      glossary: CUSTOMER.ID     # referensi glosarium (tidak divalidasi di fase ini)
      classification: pii       # public | internal | confidential | sensitive | pii
```

Ketentuan:

- **Seluruh blok opsional, seluruh properti di dalamnya opsional.** Kontrak tanpa `semantic` tetap valid dan bermakna penuh — **tanpa migration**. `Model` memakai default Pydantic v2 (`extra=ignore`) dan validator YAML import tidak menolak unknown key, jadi dokumen lama maupun baru saling kompatibel dua arah.
- **`description` tidak diganti.** Free-text untuk manusia tetap kanonik sebagai dokumentasi; `semantic` menambah makna terstruktur di sampingnya. Keduanya saling melengkapi.
- **Column-centric, bukan registry.** Metadata semantik melekat pada kolom di kontrak itu sendiri. Registry terpisah sengaja **tidak** diperkenalkan di fase ini (lihat Alternatif yang ditolak).
- **Pola strict-write/lenient-read** (mengikuti ADR-0008): `classification` adalah enum tertutup yang ditegakkan di write-path (`/datacontract/add`, `/update`, YAML validate/import → 422); read-path menerima nilai asing dari dokumen lama apa adanya tanpa 500. `entity`, `concept`, `glossary` free-text — belum ada sumber kebenaran untuk divalidasi.
- **`canonical` murni dokumentatif di v1.** Tanpa registry, keunikan "satu kolom kanonik per `(entity, concept)`" tidak bisa ditegakkan lintas kontrak. Field ini merekam *niat*, bukan invarian yang dijamin sistem.
- **Standard bump minor** `0.2.0 → 0.3.0` (field opsional baru, additive).

### `classification` vs `is_pii` — keduanya jalan, derivasi satu arah

`is_pii` adalah field **wajib** di spec, dan converter ODCS sudah memakainya: export menulis `classification: "confidential"` bila `is_pii` true, import membacanya balik ([`odcs.py`](../../repository/app/addons/converters/odcs.py)). Menambah `semantic.classification` berarti dua field memperebutkan slot ODCS `classification` yang sama.

Resolusi:

| Arah | Aturan |
|---|---|
| **Model internal** | `is_pii` tetap wajib dan tidak berubah maknanya (flag teknis boolean). `semantic.classification` opsional, lebih kaya, dan **tidak menggantikannya**. |
| **Export ODCS** | Pakai `semantic.classification` bila ada; selainnya turunkan dari `is_pii` (perilaku sekarang, tidak berubah untuk kontrak lama). |
| **Import ODCS** | `classification` → `semantic.classification`; `is_pii = true` bila nilainya `pii` atau `sensitive`. |
| **Kontradiksi** | `is_pii: false` + `classification: pii` (atau sebaliknya) = **warning**, bukan error. Kontrak tetap tersimpan; pengguna yang memutuskan. |

Properti semantik lain (`entity`, `concept`, `canonical`, `glossary`) tidak punya padanan ODCS — disimpan sebagai `customProperties` agar round-trip lossless, tercatat sebagai divergensi di [comparison-odcs.md](../../data-contract/docs/comparison-odcs.md).

### Catatan: `classification` mencampur dua sumbu

Nilai enum `public | internal | confidential | sensitive` adalah **tingkat kerahasiaan**, sedangkan `pii` adalah **kategori data**. Sebuah kolom bisa PII *dan* confidential sekaligus — satu field tidak bisa menyatakan keduanya.

Ini keterbatasan yang **diterima secara sadar** untuk v1: satu enum datar lebih ringan, dan ODCS pun memodelkannya begitu, sehingga interoperabilitas terjaga. Bila kelak terbukti perlu, pemisahan menjadi `classification` (tingkat) + `categories[]` (kategori) adalah perubahan additive — `pii` diturunkan menjadi `categories: [pii]` dengan pembacaan legacy yang lenient.

## Alternatif yang ditolak

- **Semantic Registry terpisah** — koleksi konsep tersendiri yang dirujuk kolom lewat ID. Benar secara arsitektur untuk jangka panjang, tapi menuntut CRUD registry, tata kelola, dan resolusi lintas kontrak sebelum satu pun manfaat terasa. Keputusan ini sengaja mendahulukan bentuk data; registry bisa ditambahkan kelak dengan mempromosikan `(entity, concept)` menjadi entri registry — `semantic` yang sudah ada tetap valid sebagai referensi.
- **Perluas `tags[]` dengan konvensi penamaan** (`entity:Customer`) — nol perubahan skema, tapi memindahkan struktur ke dalam konvensi string yang tidak tervalidasi, tidak bisa di-render sebagai form, dan mudah salah ketik. `tags` adalah label bebas; makna bisnis pantas mendapat tempat sendiri.
- **Tidak disimpan di kontrak, serahkan ke katalog eksternal** — makna bisnis sebuah kolom adalah bagian dari kesepakatan producer–consumer, sama seperti argumen ADR-0008 soal `on_failure`. Menaruhnya di luar kontrak berarti kesepakatan tidak lengkap, dan konsumen eksternal harus mengintegrasikan dua sistem.

## Konsekuensi

- Konsumen eksternal (HoneyGrade [#145](https://github.com/alamanda-projects/beescout/issues/145)/[#147](https://github.com/alamanda-projects/beescout/issues/147)) dapat mencocokkan kolom lintas kontrak lewat `(entity, concept)` tanpa menebak dari nama kolom.
- FE menampilkan grup "Makna Bisnis" per kolom (collapsed secara default) — biz mode menonjolkan `entity`/`concept`, eng mode menampilkan seluruhnya.
- Ada dua tempat yang menyinggung kerahasiaan data (`is_pii` dan `semantic.classification`). Aturan derivasi di atas adalah satu-satunya sumber kebenaran; jangan tambahkan tempat ketiga.
- Menambah properti semantik baru kelak = minor bump berikutnya + update write-path; mempromosikan ke registry = ADR baru yang men-*supersede* bagian "column-centric" ADR ini, bukan seluruhnya.
